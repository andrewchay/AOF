# 语义中间层接口契约（AOF）

> 当前契约（2026-09-05）：传统 topic 构建接口仍可用，但企业知识的发布和消费必须经由受治理的 release 生命周期。本文件后半部分的 mapping/regression 产物是来源和候选资产，不能绕过验证、审批与 release-pinned 消费。

## 受治理语义契约

### 生命周期

```text
KnowledgeSource / SourceBatch
  -> SemanticResource（digest + evidence references）
  -> semantic proposal
  -> validate + impact + review/waiver
  -> compile targets
  -> signed KnowledgeRelease
  -> channel promotion
  -> query/action receipt + replay
```

### REST 控制面

| 目的 | 端点 |
|---|---|
| 提案、验证、审批、编译、发布 | `/v1/semantic/proposals/*`、`/v1/semantic/releases/{release_id}` |
| 计划、执行、重放和 promotion | `/v1/semantic/compiler/*` |
| 受控查询与回放 | `/v1/semantic/query`、`/v1/semantic/query-runs/*` |
| 来源注册、摄入、暂存 | `/v1/knowledge/sources/*`、`/v1/knowledge/ingestion-runs/*` |
| 本体草案和 release | `/v1/ontology/*` |
| Agentic 查询、回放和会话 | `/v1/agentic/*` |

上述受控操作需要六个 `x-aof-principal-*` 签名头：subject、tenant、roles、timestamp、key-id、signature。服务从该 principal 推导权限和 tenant；body 内 `actor` 为兼容字段且被忽略。传统 `/v1/reasoning/*` 和原始 ontology MCP 工具尚未统一到这一边界，不能直接暴露为企业多租户接口。`POST /v1/semantic/compile` 返回 `410 Gone`，替代端点为 `/v1/semantic/query`。

### 消费约束

- `channel`、`capability`、`purpose`、`policy_resource_id` 和 `rationale` 是 query 的必填控制信息。
- 返回值必须可以关联 release、query run、证据包和 digest；消费者不得只保留生成文本。
- graph、vector、关系数据和 Skill 消费均须指向同一 release。

---

## 定位

AOF 在企业数据栈中的角色是“语义中间层”：

- 上游只提供：`文档`、`元数据`、`反馈`
- 中间层负责产出：`OWL`、`业务 mapping 库`、`回归样例库`
- 下游消费：Text-to-SQL、BI Copilot、指标治理、查询审计、语义检索、规则引擎

## 上游输入接口

### 1) 文档输入（必需）

- SQL 样例（.sql）
- 口径文档（.md/.txt）
- 历史分析报告（.md/.txt）
- 看板字段说明（.md/.txt/.json）

要求：
- 文档目录可递归扫描
- SQL 尽量保留注释，便于自动生成回归样例的问题描述

### 2) 元数据输入（推荐）

JSON 结构建议：

```json
{
  "tables": [
    {
      "name": "dws_community.dws_community_user_login_snapshot",
      "columns": [
        {"name": "logdate", "type": "date"},
        {"name": "account_id", "type": "bigint"}
      ]
    }
  ]
}
```

### 3) 反馈输入（可迭代）

`feedback.jsonl`（每行一条 patch）：

```json
{"action":"map_term","term":"miyoushe_dau","class":"CommunityMetric"}
{"action":"add_class","name":"BusinessConstraint"}
{"action":"add_relation","source":"sql_query_1","predicate":"usesFilterCondition","target":"snapshot_date_t_minus_1"}
```

## 中间层输出接口

### 1) 本体产物

- `TEST_DATA_<topic>_ontology.owl`
- 对齐报告（json/md）
- 模式分析（json/md）
- 待评审反馈清单（jsonl/md）

### 2) 业务 mapping 库

目录：`data/middle_layer/<topic>/mapping/`

- `term_mapping.yaml`
- `metric_catalog.yaml`
- `dimension_mapping.yaml`
- `sql_pattern_library.yaml`

### 3) 回归样例库

目录：`data/middle_layer/<topic>/regression/`

- `regression_cases_<topic>_<ts>.jsonl`
- `regression_summary_<topic>_<ts>.md`

### 4) 产物清单

目录：`data/middle_layer/<topic>/artifacts/`

- `middle_layer_manifest_<topic>_<ts>.json`
- `skills_update_suggestions_<topic>_<ts>.md`

## 下游消费建议

### Text-to-SQL

- 用 `term_mapping` 做术语归一
- 用 `metric_catalog` 做指标口径约束
- 用 `dimension_mapping` 做字段定位
- 用 `sql_pattern_library` 做 SQL 生成模板约束
- 用 `regression_cases` 做离线回归门禁

### BI Copilot / 语义问答

- 先查 `term_mapping` 与 `OWL`
- 再生成解释：术语 -> 指标定义 -> 过滤条件 -> 数据源

### 指标治理 / 报告审计

- 对照 `metric_catalog.required_filters`
- 自动检查报告 SQL/看板 SQL 是否符合口径

### 查询审计 / 合规

- 将敏感字段标注纳入 `dimension_mapping`
- 下游调用前先做规则检查

## 闭环更新机制

1. 下游发现错误（SQL、口径、实体关系）
2. 转成 `feedback.jsonl` patch
3. 重跑中间层构建
4. 产出新 OWL + 新 mapping + 新 regression
5. 下游回归通过后发布

LLM_API_KEY="<YOUR_KEY>" \
